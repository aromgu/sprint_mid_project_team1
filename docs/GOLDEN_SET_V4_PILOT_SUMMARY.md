# Golden Set v4 Pilot 요약

## 목표

전체 98개 RFP를 한 번에 처리하지 않는다. 먼저 대표성 있는 RFP 10개를 선정하여 문서당 10문항, 총 100문항의 Pilot Golden Set을 완성한다.

Pilot을 생성·검수·평가하면서 발견한 오류와 개선점을 다음 배치에 반영한 뒤 전체 문서로 확장한다.

## 버전 정의

- 기존 데이터: `goldenset/golden_set_v3.jsonl`
- 새 Pilot 결과: `goldenset/golden_set_v4_pilot.jsonl`
- Pilot 검증 후 전체 확장본: `goldenset/golden_set_v4.jsonl`

새 가이드는 v3의 문서·섹션·필수 사실 기반 평가에 페이지·청크·직접 인용 검수 필드를 추가한 `v3+` 구조다. 새 결과물의 명칭은 v4로 관리한다.

| 항목 | 결과 |
|---|---:|

| 답변 가능 | 95개 |

## v4 Pilot 문항 구성

문서당 10문항을 다음과 같이 구성한다.

### 답변 가능 여부

- 답변 가능: 9개
- 답변 불가능: 1개

전체 100문항 기준으로 답변 가능 90개, 답변 불가능 10개를 목표로 한다.

### 난이도

- Easy: 문서당 3개, 전체 30개
- Medium: 문서당 4개, 전체 40개
- Hard: 문서당 3개, 전체 30개

목표 비율은 `Easy 30% / Medium 40% / Hard 30%`다.

### 멀티홉

- 문서당 3개
- 전체 30개
- 전체 문항의 30%
- 답변 가능 문항 기준 약 33.3%

멀티홉 문항은 다음 조건을 모두 만족해야 한다.

1. 서로 다른 페이지 또는 섹션의 근거가 두 개 이상 필요하다.
2. 근거 하나만으로 완전한 답변을 만들 수 없다.
3. 각 근거가 서로 다른 `required_fact`를 뒷받침한다.
4. 실제 필요한 근거 단위 수를 `hop_count`에 기록한다.

한 청크에 포함된 목록을 단순 나열하거나 같은 표 안에서 여러 값을 찾는 질문은 멀티홉으로 분류하지 않는다.

Pilot 평가 후 복합 질문 누락 문제가 반복되면 다음 배치에서 멀티홉 비중을 40%까지 높일 수 있다.

## 문서 선정

목록 앞의 10개를 그대로 사용하지 않는다. 다음 특성이 가능한 한 포함되도록 대표성 있는 문서를 선정한다.

- 텍스트 추출이 양호한 일반 문서
- 요구사항 표가 많은 문서
- 장문 또는 섹션 구조가 복잡한 문서
- OCR 또는 파싱 품질이 낮은 문서
- 참가 자격·실격·계약 조건이 복잡한 문서
- 보안·성능 요구사항이 많은 문서

선정 문서, 선정 사유, 난수 seed를 별도 manifest에 기록한다.

## 핵심 데이터 필드

v4 Pilot은 다음 기준을 함께 기록한다.

### 안정적인 평가 기준

- `document_id`
- `source_document`
- `gold_sections`
- `gold_sections_optional`
- `ground_truth`
- `required_facts`
- `answerable`

### 원문 검수 및 추적 기준

- `reference_context_ids`
- `reference_pages`
- `evidence_quotes`

존재하지 않는 청크 ID를 임의로 만들지 않는다. 청크를 확정할 수 없으면 `reference_context_ids`를 빈 배열로 두고 `review_status=needs_chunk_mapping`으로 기록한다.

## 작업 순서

```text
대표 문서 10개 선정
→ PDF·청크·섹션 매핑 점검
→ 문서별 정답 근거 선정
→ 문서당 10문항 초안 생성
→ 별도 세션 또는 별도 모델로 독립 검증
→ JSONL 자동 품질 검사
→ 사람이 PDF 원문과 대조
→ 승인·수정·반려 상태 기록
→ 개발·검증·최종 테스트셋 분리
→ Retriever 및 답변 생성 평가
→ 실패 유형 분석
→ 프롬프트와 검수 기준 개선
→ 전체 문서로 단계적 확장
```

100문항을 한 번에 생성하지 않는다. 문서 하나씩 생성하고 검수한다. 첫 두 문서를 완료한 시점에 오류 유형을 검토하고 프롬프트를 한 차례 보정한다.

## Split

| 구분 | 문항 수 | 용도 |
|---|---:|---|
| 개발셋 | 60 | 청킹·검색·프롬프트 개선 |
| 검증셋 | 20 | 설정과 모델 선택 |
| 최종 테스트셋 | 20 | 확정 구성의 최종 측정 |

같은 섹션이나 동일 근거에서 파생된 유사 문항은 동일 split에 배치한다. 최종 테스트셋을 보고 시스템을 튜닝하지 않는다.

## 전체 확장 원칙

10개 문서와 100문항의 생성·독립 검증·자동 검사·사람 검수를 모두 완료한 뒤 전체 98개로 확장한다.

확장 단계에서도 한 번에 처리하지 않고 5~10개 문서 단위 배치로 진행한다. 각 배치가 끝날 때 품질 결과와 실패 유형을 기록한다.
